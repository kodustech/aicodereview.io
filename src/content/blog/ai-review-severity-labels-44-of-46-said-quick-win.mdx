Severity labels are the part of an AI review people trust without checking. They are also the part least likely to mean the same thing across tools. If your comparison of code review tools sorts by "critical issues found", you are sorting by a number the tool assigned to itself.

I pulled 30 merged pull requests from the week of 2026-11-08 through 2026-11-14, matching `reviewed-by:coderabbitai[bot]` on the GitHub search API, and read every inline comment on each one. 75 inline comments total. 51 were top-level findings, 24 were replies inside existing threads.

Of the 51 top-level comments, 46 carried the same structured header line: a severity word, a category, and an effort tag. Two carried a different scheme entirely (I'll get to that). Three had no label line at all.

The severity split across those 46 was 10 Major and 36 Minor. The effort tag was 44 "Quick win" and 2 "Heavy lift". So 95.7% of labeled findings were rated easy, and 78% were rated minor.

That distribution is the thing to look at. If you are scoring a tool by how many Major findings it produces, this is the baseline you are scoring against: a reviewer that labels most of its output Minor and almost all of it a quick win.

## A label is a claim about the reviewer

Severity is not measured. It is generated by the same model that generated the finding, in the same pass, with no ground truth attached. The vendor documentation describes it as a classification the reviewer applies to its own output. There is no calibration step where a human or a second model confirms that a "Major" is actually major.

The [CR-Bench-v2 paper](https://arxiv.org/html/2611.02566v1) makes the same point from the other direction. It builds a defect-centric benchmark where each instance has a known defect, a ground-truth fix, and a taxonomy label for bug category, impact, and severity, then measures whether agents actually find the labeled defect. Even the strongest systems detect about one third of known defects (KDDR around 33%), and the paper explicitly separates defect detection from developer utility because those two numbers do not track each other. A finding can be real and still be useless to the person reading it, and the tool's own severity tag is not evidence either way.

The [Vibe Coding review](https://arxiv.org/html/2608.20446v1) collects the productivity record for AI-assisted development and notes code review time up 441% in team-level telemetry, with noisy comments cited as a reason engineers slow down adoption. Volume of findings is easy to produce. Prioritization is the hard part, and the severity label is the vendor's attempt at it, generated by the thing being evaluated.

## Two label schemes from one vendor

Here is the part that should change how you read a comparison table. Two of the comments in that same cohort, from two repositories owned by the same author, did not use the Major/Minor vocabulary at all. They used a badge with `P1` and `P2` in it, rendered as an image at the top of the comment:

```
**![P2 Badge](badge/P2-yellow?style=flat)  Update the documented duplication-gate ranking
```

That is a priority scheme, not a severity scheme, and it is a different vocabulary from the Major/Minor line that 46 other comments used. It appears in two repositories, both maintained by the same person, which suggests it may be a setting the author enabled rather than a rollout. Either way, one vendor shipped two label vocabularies into the same week of merged PRs.

If your comparison script parses severity by looking for the word "Major" or "Minor", those two comments are invisible. If it parses by looking for a badge color, the other 46 are invisible. Neither script is wrong. Both are measuring a subset, and neither subset is the tool's real severity behavior.

There is a related trap in the [4-field audit of merged AI agent PRs](https://aicodereview.io/blog/merged-ai-agent-prs-zero-reviews-a-4-field-audit/): counting review objects tells you nothing about whether a review happened. Labels have the same failure mode. A labeled comment is not a finding with a severity. It is a finding plus a string.

## Why the low-severity bucket is the expensive one

The instinct when comparing tools is to count the scary labels. That is backwards, for a mechanical reason. A finding the reviewer calls Major gets read. A finding called Minor, on a PR that already has a green check, is the one that gets skimmed past and merged.

In the same cohort I checked whether each off-head comment sat on a path that changed again between the comment's commit and the PR head. 26 of 26 did. The files the reviewer had flagged kept moving before merge. That means a "Minor" label attached to a file that was edited three more times after the comment landed is describing a moving target, and the label was assigned when the file looked different from its final state.

This is the same shape as the [coverage gap in 9 of 28 merged PRs](https://aicodereview.io/blog/9-of-28-merged-prs-had-code-the-ai-reviewer-never-saw/) and the [absence blindness problem](https://aicodereview.io/blog/your-reviewer-blocked-the-pr-did-it-name-the-bug/): what the reviewer did not label is harder to audit than what it did, and the tool's own categories make the missing part harder to see because every category looks populated.

## A calibration you can run before you rank tools

Do this on the actual shortlist rather than on marketing pages. It takes an afternoon and it works on CodeRabbit, Greptile, Qodo Merge, Kodus, or whatever else is in the running, because every one of them leaves the same API surface.

Pull 50 top-level inline comments per tool from merged PRs in a single week, using the vendor's review bot login in the `reviewed-by:` qualifier. Then record four numbers per tool.

First, the severity distribution. If a tool labels 78% of its findings Minor, that is the number you compare against the other tool's number, not a headline count of "issues found".

Second, the label coverage. Divide top-level comments that carry a parseable severity by total top-level comments. In this cohort that was 46 of 51, or 90.2%. Coverage below 100% means your parser and the tool disagree about what a label is, and a comparison built on that parser will silently drop rows.

Third, the vocabulary count. Grep for every distinct label token the tool emits across the sample, including tokens inside image URLs, since that is where the second scheme hid. More than one vocabulary in one week is a warning that severity is configurable and therefore not comparable across teams.

Fourth, the fix proxy. For each comment, compare the comment's `commit_id` to the PR head with the compare API and check whether the commented path changed again. A high rate means you are reading labels assigned to revisions that no longer exist.

## What to do with the label once you have it

Keep the severity tag as a triage hint inside one repository where the same configuration produced it. Do not carry it across tools, and do not put it in a comparison table without the distribution next to it. The label describes the reviewer's tone that day, on that revision, under that team's configuration.

For the thing severity was supposed to answer, which findings actually matter, use something with ground truth behind it. Seed a PR with a defect you planted, run each tool, and check whether the tool found that defect. The [ground-truth-first approach to benchmarking](https://aicodereview.io/blog/ai-code-review-benchmark-read-the-ground-truth-first/) is slower than parsing labels and it is the only version of the comparison that survives a second week.

The honest version of a severity claim looks like this: "46 of 46 labeled findings carried a severity word, 78% were Minor, and the labels came from the reviewer's own classification with no external confirmation." Anything shorter than that is a string the tool wrote about itself, and you are about to make a purchasing decision on it.

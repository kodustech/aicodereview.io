A merged PR with a resolved review thread reads like evidence. The bot raised something, a human replied, the conversation closed, the code shipped. Plenty of teams treat that as their "a person looked at this" signal, especially now that the code being reviewed is often generated too.

I pulled the reply threads under AI review comments on 23 merged pull requests from a single week and split the replies by who wrote them. GitHub gave me 32 replies from logins with `user.type` set to `User`. All 32 came from the PR author. Zero came from any other human. And 12 of the 32, about 37.5%, carried an in-body agent marker, the kind of tag an assistant leaves when it posts on a person's behalf.

That last number is the one I keep coming back to. The reply thread is the only part of an AI review that still looks like human judgment, and it is also the part where one agent is most likely to be answering another agent.

## The cohort, and how to rebuild it

Everything below comes from the unauthenticated GitHub REST API, so you can reproduce it in an afternoon. Start with the search endpoint:

`is:pr is:merged reviewed-by:coderabbitai[bot] merged:2026-11-08..2026-11-14` returns a `total_count` of 126,419. Swap the login to `greptile-apps[bot]` and the same window returns 24,706. Those are the two arms I sampled.

From there I walked the newest 23 merged PRs and called `GET /repos/{owner}/{repo}/pulls/{number}/comments` on each. Top-level comments are the ones where `in_reply_to_id` is null. Replies are comments whose `in_reply_to_id` points at a top-level comment. That is the whole mechanism, and it is documented in the [REST API for pull request review comments](https://docs.github.com/en/rest/pulls/comments?apiVersion=2022-11-28), where replies come back in the same list as the comments they answer.

One classification note that matters for the numbers: `user.type` tells you whether the login is a bot account or a person, and it will happily tell you a reply is human when a human's own agent posted it. A reply from `Arunjay4213` is `type: User`. The body starts with `[Arunjay's Claude]`. So I ran a second pass with a regex over the reply body looking for a bracketed agent tag, `generated by`, or a `co-authored-by` trailer. 12 of the 32 replies matched.

## What the 45 comments did

Across those 23 PRs the two reviewers left 45 top-level inline comments. The reply distribution:

- 26 of 45, or 57.8%, got at least one human-login reply.
- 7 of 45, or 15.6%, got a reply from another bot.
- 17 of 45, or 37.8%, got no reply at all.

So the "everyone ignores the AI reviewer" story is too simple. On this sample, more than half the comments started a conversation. The problem is who was in it.

## All 32 replies came from the PR author

This is the field I would put at the top of any review-tool evaluation. 32 replies, 32 distinct from the person who opened the PR. Seven PR authors and seven responder logins in the sample, and the sets are identical. Nobody else joined a single thread.

The cleanest example is [meetsanctum/sanctum#49](https://github.com/meetsanctum/sanctum/pull/49). The reviewer raised three points, and the author answered each one with a specific commit: `Fixed in 1e27f8d5` and `Changed in 7a363037`. I checked both hashes against the PR's commit list, and both are there. The replies landed at 23:47 and 23:56 UTC. The PR merged at 23:58:42. That is a tight, honest loop, and it is still the author grading their own homework.

Now the version that should make you uncomfortable. On [Arunjay4213/MadHacks#108](https://github.com/Arunjay4213/MadHacks/pull/108) the replies are agent-written and one of them is a correction to an earlier agent-written reply. The first says the fix is in `#146`. A later one says the work actually landed through `#148` and `#146` no longer carries it. When I pulled the files changed by `#146`, the path the original comment was attached to was not in the list. The pointer had moved, and the only thing that noticed was the same agent that wrote the pointer.

If your gate is "the thread is resolved", you are counting one party agreeing with a tool, sometimes through a second tool.

## Two reply populations, split at ten minutes

Latency separates the two kinds of reply almost cleanly. Replies that arrived under ten minutes after the comment: 17, of which 2 carried an agent marker, about 12%. Replies that took ten minutes or more: 15, of which 10 carried an agent marker, about 67%.

Median reply delay by vendor, within this sample: 3.2 minutes for the CodeRabbit arm (10 replies) and 61.4 minutes for the Greptile arm (22 replies). Read that next to the marker rates and you get a useful model. The fast replies are a person reading a diff and reacting. The slow ones are a batch job where the author pointed an agent at the review threads and let it write the responses, then posted them as their own account.

That matters for measurement because the two populations have different failure modes. A human reply might be wrong about the code. An agent reply might be wrong about which commit, which PR, or whether the fix exists at all, and it will write it in the same confident first-person voice as the person it is standing in for.

## "Fixed in" is a claim you can resolve

You do not have to take the reply's word for anything. Both citation styles are checkable with two API calls.

If the reply names a SHA, compare it to `GET /repos/{owner}/{repo}/pulls/{number}/commits`. In the 32-reply sample, 12 replies cited a SHA and 11 of them resolved against the PR's own commit list. In an earlier 19-reply slice I ran the same check on the PR-number style: 10 replies cited a `#N` reference, and 6 of those cited PRs touched the file the original comment was attached to. Four did not. Two of the four are the MadHacks case above.

That 6-of-10 is not a verdict on either vendor. It is the argument for making the check part of your evaluation instead of trusting the reply text. A citation that does not resolve is a broken link in the audit trail, and it is invisible if you only read the thread and see "Fixed in #146" in green-looking prose.

## The 4-field reply-thread audit

Record these four fields per tool, per review thread. They take one script and they survive vendor changes.

1. `reply_author_type`, split three ways: PR author, other human, bot. Report the count of replies that came from a login which is not the PR author. On my sample that number is zero.
2. `agent_marker`, a boolean from a body regex. Report the share of human-login replies that match. Mine was 37.5%.
3. `reply_latency_minutes`, as a distribution, not a median. The under-ten-minute and over-ten-minute buckets have different marker rates, 12% against 67%, and a single median hides that.
4. `citation_resolves`, a boolean per reply, true when the cited SHA is in the PR's commit list or the cited PR's changed files include the commented path. Mine was 11 of 12 for SHAs and 6 of 10 for PR numbers.

The decision rule that falls out of this: if a resolved thread counts toward your review coverage, require at least one reply from a login that is neither the PR author nor agent-marked. Otherwise the metric is a conversation, not a verification. The wider case for independent verification over self-review is the same argument I made in [your AI reviewer is judging its own output](https://aicodereview.io/blog/your-ai-reviewer-is-judging-its-own-output-thats-a-blind-spot/), just one level down the stack.

## What to change in the gate

The fix is mostly process, and the tools decide how easy it is.

GitHub gives you `CODEOWNERS` and required reviewers, and that is the only mechanism that reliably puts a second human in the thread. If a bot's comment is the trigger and the author's account is the only responder, you have a monologue with a merge button.

On the tool side, what you want to check before buying is whether the reviewer's comments can be resolved by anyone other than the author, and whether the thread history stays queryable after the fact. CodeRabbit ships a prompt block in its comments that hands the finding to an agent, which is exactly the path that produced the agent-marked replies above, so decide deliberately whether you want that. Greptile's summary lands as an issue comment rather than a review object, which is worth knowing when you build the collector. GitHub Copilot code review is convenient if you already pay for it, and its documented file skips mean your coverage numbers start with a hole. Qodo Merge is the option to look at when you want the model choice in your own hands. Kodus is the one I would test first for this specific problem, because it self-hosts and reads your rules from files your repo already has, so the review threads and the replies to them stay inside infrastructure you control while you run the audit.

None of that changes the underlying shape. The volume of AI-generated code is going up, and the review time is going up with it. The [Vibe Coding state-of-the-art review](https://arxiv.org/html/2608.20446v1) collects the field evidence and notes team telemetry showing code-review time up 441%, against peer-reviewed field experiments at plus 26% more tasks per week and independent randomised trials measuring a 19% slowdown. When review load grows, the cheapest thing to automate is the reply. That is what the 37.5% is.

Run the four fields on your own merged PRs this week. If the "other human" count in field one is zero for your repos too, the thread was never the gate you thought it was.
